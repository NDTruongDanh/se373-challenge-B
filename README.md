# SE373 Challenge B — Memory, Context Engineering & Prompt Caching

Implements **Challenges B1 and B2** of the _Memory, Context Engineering & Prompt Caching_ module (SE373).

Two complementary techniques for keeping LLM context small while the agent still gets the job done, proven against one shared log fixture:

- **B1: Compact** — a long debugging session full of large logs gets compacted to a 7-field structured checkpoint; the agent resumes from the checkpoint alone.
- **B2: Code Mode** — the agent answers a question spanning many logs by writing one program that aggregates inside the runtime; only the small `result` returns to context, raw logs never do.

## Shared fixture & ground truth

Both challenges run against the same synthetic logs (generated by `B1/generate_logs.py`, stored at repo root so B2 reuses them):

```
logs/
├── app.log         ~2,000 lines: INFO noise + duplicated WARNs + 3 real ERRORs
├── test_run.log    ~7,000 lines: pass noise + 3 buried FAILEDs + HINT/NOTE/PLAN lines
└── grep_noise.log  ~1,500 lines: grep matches, mostly noise
```

The ground truth buried in the logs (what a correct B1 checkpoint / B2 answer must contain):

| Item                   | Value                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------ |
| Failing tests          | `test_concurrent_refresh`, `test_session_expiry_retry`, `test_lock_around_refresh`   |
| Root cause             | race in `SessionStore.refresh()` — read-modify-write with no lock held               |
| Already tried (failed) | increasing token TTL to 3600s; naive retry loop ×3                                   |
| Constraint             | keep API backward compatible (`login`/`refresh` signatures unchanged)                |
| Next step              | inspect locking around refresh in `dummy_app/session.py` (`B1/dummy_app/session.py`) |

Shared config also lives at the root: `.env` (template: `.example.env`) holds the Go inference key / base URL / models / `TOKEN_BUDGET` and is loaded by both `B1/src/config.py` and `B2/src/config.py`.

## B1: Compact — keep context small while the agent still gets the job done

**Goal:** a long debugging session full of large logs gets compacted, and the agent still remembers the three things that matter: (1) what error is under investigation, (2) what was already tried, (3) what the next step is — while raw logs stay out of the context.

**Pipeline** (`B1/src/compaction.py`, triggered from `B1/src/agent_graph.py`): **Observe → Prune → Build → Reinject → Resume**

1. **Observe (trigger).** Token budget check every round (`TOKEN_BUDGET`, default 8000); counts from real `usage_metadata` + tiktoken (`cl100k_base`) estimate with char÷4 fallback.
2. **Prune (deterministic, no LLM).** `prune_notes()` (oversized outputs → TRUNCATE, duplicate lines → DROP) + `signal_excerpt()` (first 40 lines + every `FAILED`/`ERROR`/`HINT`/`NOTE`/`PLAN`/`SUMMARY`/race line, de-duplicated, ≤12k chars). Slide 23 rules verbatim: KEEP decisions/constraints/failing test names; TRUNCATE unresolved errors; DROP duplicates/concluded retries.
3. **Build (LLM-call summary).** `COMPACT_INSTRUCTION` demands JSON-only with exactly the 7 Structured Checkpoint fields from slide 22 (`goal, current_state, constraints, findings, failed_attempts, files, next_action`); schema-validated. `heuristic_checkpoint()` (regex) covers the no-key path used by `verify.py` / `demo.py --no-agent`; live runs raise loudly on LLM failure, no silent fallback.
4. **Reinject.** New context = `[checkpoint.md as SystemMessage + last 2 messages]`; true replacement via `RemoveMessage`, plus a one-line JSON record in `B1/archive/session_full.jsonl`.
5. **Resume.** Agent continues from checkpoint only, instructed not to re-read raw logs.

**Run it:**

```powershell
cd B1
uv venv; uv sync
copy ..\.example.env ..\.env   # then paste your key
uv run python generate_logs.py # regenerates ../logs/
uv run python verify.py            # no key, no network
uv run python demo.py --no-agent   # deterministic, offline
uv run python demo.py              # full live run: agent loop + LLM compact + LLM quiz
```

**Measured results:** 9 msgs / ~223,800 tokens / ~600KB raw output → 3 msgs / ~500–600 tokens (**99.7–99.8% reduction**); post-compact quiz: error ✅ / tried ✅ / next ✅, no raw leak ✅. Details in `B1/README.md`.

## B2: Code Mode — answer over many logs without raw logs in context

**Goal:** answer a question spanning `logs/app.log` (~2,000 lines), `logs/test_run.log` (~7,000 lines) and `logs/grep_noise.log` (~1,500 lines), while raw logs never enter the LLM context — only the aggregated `result` does.

**Design** (`B2/src/`): **Write → Run → Receive.** The LLM returns a single `run_code` tool call carrying a Python program; the runtime executes it against an internal SDK (`list_logs, read_lines, grep_count, grep_matches`, every scanned byte counted); the model receives only the small aggregated `result` (~600KB scanned inside, ~200 chars returned).

- Native vs Code Mode: same tool shape, moved loop — native = LLM↔tool per file (every raw output lands in context); Code Mode = code loops/aggregates inside the runtime, one small return.
- Runtime: in-process `exec()` with restricted builtins, denylist (`import`/`open`/dunders), path confinement to `logs/`, 5s timeout, `result` cap (≤2000 chars, ≤50 lines) — a demo-grade sandbox, not a security boundary.
- Measurement via real `usage_metadata` + tiktoken estimates; scanned-vs-returned counters from `RAW_STATS`.

**Run it:**

```powershell
cd B2
uv venv; uv sync
# .env already at repo root; regenerate logs if needed:
uv run python ../B1/generate_logs.py
uv run python verify.py            # offline, no key
uv run python demo.py --no-agent   # offline: canonical program + context report
uv run python demo.py              # live: LLM writes the program (needs key in ../.env)
```

**Measured results (offline, deterministic):** ~1.6MB / ~31k lines scanned in 6 SDK calls → <1KB returned (558 chars canonical, ~2900x reduction); LLM context = task + result only (~650 est. tokens); answer checks (failed_tests / app_error_count / grep_count / hint / tried / next) ✅, raw leak none ✅. Details in `B2/README.md`.

## Connection details (shared)

Both harnesses talk to the direct Go inference endpoint (`https://opencode.ai/inference/go/openai/v1`, override with `OPENAI_BASE_URL`); auth is the Go API key (`OPENCODE_API_KEY`, fallback `OPENAI_API_KEY`). `x-opencode-session` is a client-chosen stable id per conversation (routing/prompt caching), from `OPENCODE_SESSION_ID` when present else generated per run, always sent with our own `User-Agent`. The `*-contributor` models speak the responses protocol, so the harness builds `ChatOpenAI(use_responses_api=True)`.
